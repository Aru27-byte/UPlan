# File Structure and Imports

## Repository layout

```
CLAUDE.md
Requirements/            product docs and feature requirements
TechDesign/              system design and feature designs
.claude/                 skills and these rules
package.json, package-lock.json, tsconfig.json, next.config.ts,
eslint.config.js, vitest.config.ts, playwright.config.ts, drizzle.config.ts
Dockerfile               three targets: web, worker, postgres
src/
  proxy.ts               redirects signed-out page visits; not a security boundary
  app/                   Next.js routes only: pages, layouts, route handlers, Server Functions
  modules/
    <module>/
      index.ts           the module's public API, and the only file other code imports
      tables.ts          the Drizzle tables this module owns
      <concern>.ts       domain logic, one concern per file
      <concern>.test.ts  tests beside the code they test
  ui/                    React components shared by more than one route
  worker/
    main.ts              worker entry point, bundled by esbuild
    tasks.ts             task registry: task name to module function
  platform/              database pool, object storage client, model server client, environment, logger, errors, auth wiring
migrations/              generated by drizzle-kit
tests/e2e/               Playwright specs
deploy/                  compose.yaml, Caddyfile, models.ini, backup timer units, setup.sh, deploy.sh
```

Modules are `accounts`, `profiles`, `provenance`, `evidence`, `decisions`, `analysis`, `reports`, `records`, and `operations`, with `code-tracking` and `conditions` coming later in v1. A new module needs a row in the module table in `TechDesign/system-architecture.md` before any code.

## Where code goes

- Domain rules, SQL, and transactions go in the owning module, never in `src/app/`, `src/ui/`, or `src/worker/`.
- Routes and job tasks stay thin: authenticate, validate input, call one module function, and return or record the result.
- A component used by one route lives in that route's folder. It moves to `src/ui/` only when a second route needs it.
- Client components live in `*.client.tsx` files. These files and everything in `src/ui/` never import runtime code from `src/modules/` or `src/platform/`; `import type` is allowed.
- Tests sit beside the code as `*.test.ts`. End-to-end specs go in `tests/e2e/`.
- The repository root holds only the files listed above. No scratch, notes, or output folders.

## Imports

- Import from `src/` through the `@/` alias, for example `import { rulesInForce } from "@/modules/profiles";`.
- From outside a module, import only its `index.ts`. A deep import such as `@/modules/profiles/changes` from another module fails lint.
- Inside a module, use relative imports.
- `src/platform/` imports nothing from modules, routes, UI, or the worker. Modules import `platform`; routes and the worker import modules.
- Type-only imports use `import type`.
- Use named exports only. Default exports appear only where Next.js requires them, such as `page.tsx`, `layout.tsx`, and `proxy.ts`.
- No import cycles; lint enforces this.
- The only barrel files are module `index.ts` files.

## Obsolete files

- When a change leaves a file, export, route, component, or dependency unused, delete it in the same change if that change's scope covers it.
- If the scope doesn't cover it, list it in your response under **Obsolete**, with its path and why it's no longer needed. Don't leave it silently.
- Never keep dead code alive with a re-export, a deprecation comment, or a flag.
- Applied migrations are history, not obsolete files. Never edit or delete one; write a new migration.
